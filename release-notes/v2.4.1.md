# Aurelia v2.4.1

Deleting a layer no longer takes the studio down with it.

## The crash

The layer panel draws rows in reverse index order and, inside a row, the action
buttons (delete, ungroup, duplicate, add-to-folder, rasterize) mutated
`document.layers` **immediately**. Everything after those buttons still reads
`layers[i]` — blend mode, opacity, alpha lock, clip, reference, folder selector.

Deleting the top layer is the common case, and it shrinks the vector to exactly
that index, so the next read of the very same row was out of bounds and panicked.
Deleting any other layer shifted the indices of rows that had not been drawn yet,
so they would have rendered or acted on the wrong layer.

`Document::delete_layer` was not at fault: it protects the final layer and
re-points `active_layer_id`. The bug was purely *when* the UI mutated relative to
its reads.

## The fix

Structural edits are now queued while the list is drawn and applied **after** it:

```rust
enum LayerCommand {
    Delete(LayerId), Ungroup(LayerId), AddChild(LayerId),
    Duplicate(LayerId), RasterizeActiveText,
}
```

No row can observe a mutated vector any more. Nothing about the panel's layout or
behaviour changed otherwise — the same buttons do the same things, one frame
sooner or later.

While in there: **duplicate now targets the row you clicked**, not whichever layer
happened to be active.

## Verification

- Three new core tests lock down the invariants the panel depends on: deleting
  from the top down keeps at least one layer, keeps `active_layer_id` pointing at
  a live layer, and keeps every index readable; deleting a group takes its
  descendants with it; ungrouping re-parents children to the root. **68 tests pass.**
- `scripts/smoke_delete_layer.ps1` drives the real application: it adds two layers
  through the panel, deletes the top one twice, and captures a screenshot at each
  step. Clicks are posted straight to the window, so an overlapping console or
  terminal cannot swallow them and silently pass the test.

## Unchanged

Installer, portable zip, staged pipeline, SHA-256 manifest and the VirusTotal gate
behave as in 2.4.0. The installer remains unsigned, so a couple of engines still
flag generic Inno Setup heuristics; that is disclosed below and resolved by
Authenticode signing.
