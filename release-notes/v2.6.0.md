# Aurelia v2.6.0

The general compositing path, three times faster — without moving a single pixel.

## The number

Compositing a 1920×1080 stack of four layers, where one layer carries an offset and a
blend mode (the "general" path):

| | v2.5.0 | v2.6.0 | |
| :--- | ---: | ---: | ---: |
| **General path, opaque** | 25.7 MPix/s | **83.6 MPix/s** | **3.3×** |
| General, 50 % coverage | — | 128.1 MPix/s | |
| General, 10 % coverage | — | 209.5 MPix/s | |
| General, 10 % + layer mask | — | 188.4 MPix/s | |
| With a clipping layer | — | 60.4 MPix/s | |
| Plain stack (unchanged path) | 113.1 MPix/s | 160.2 MPix/s | no regression |
| With layer mask (unchanged path) | 92.6 MPix/s | 140.7 MPix/s | no regression |

Measured on an Intel Alder Lake (12 logical cores) with rustc 1.93.1, release profile,
1920×1080, 4 layers, 20 iterations × 3 interleaved rounds, best round reported. A second run of the
 same binary gave 91.4 MPix/s for the opaque general case, so treat these figures as
+-10%; the gates are met in both.

## What was actually wrong

None of the cost was the blend maths. It was work whose result was thrown away:

1. **Out-of-bounds pixels.** The loop visited every canvas pixel even for a layer offset
   into a corner; each one went through `get_pixel`, four bounds checks and an `Option`.
   The valid span is now computed per row and indexed directly.
2. **Fully transparent pixels.** `composite_pixel` returns the destination unchanged for a
   transparent source — but only after the full float path. Skipping those pixels before
   the call is exact, and on real artwork it is the dominant win: a 10 %-coverage layer
   runs 2.5× faster than a fully opaque one.
3. **Blend dispatch per pixel.** The mode was matched inside every pixel call. It is now
   resolved once per layer, and each mode runs a monomorphised loop (`compose_normal`,
   `compose_multiply`, …). The maths still lives in exactly one place.
4. **The clip base.** A clipped layer re-read its base's alpha through `get_pixel` for
   every pixel. It is now resolved to a contiguous span per row.
5. **One core.** Rows of a layer are independent, so they are now composed in parallel —
   with fixed row ownership per thread, a join before the next layer, and a size
   threshold so small canvases stay on one thread.

## Correctness

The old implementation is kept verbatim as an oracle, and every optimisation is required
to produce **byte-identical** output:

- **702 combinations** — 13 blend modes × 3 offsets (including negative) × 3 mask states ×
  clipping on/off × 3 coverages.
- **234 clipping corners** — a base whose pixel buffer ends early, a base whose size
  disagrees with the canvas, and a base of a layer kind that reports no pixel at all.
- **Parallel vs serial** — a fixture large enough to take the parallel path is compared
  against the single-threaded oracle.
- **Determinism** — repeated composites of the same document must produce the same bytes.

The oracle earned its keep twice. First it revealed that the clip-base rewrite was reading
sources at canvas stride while the reference goes through `Layer::get_pixel`, which uses
the layer's own width, height, pixel length *and* kind — the clipping corners test failed
immediately and the rewrite now reproduces `get_pixel` exactly. And a 256-entry
`n/255.0` lookup table was measured, found 19 % *slower* (a static table can alias the
output buffer, forcing reloads after every store), and reverted rather than kept because
it was expected to be faster.

## Notes

- The plain and masked paths were not modified; their numbers moved because the whole
  machine did. Every figure above comes from the same interleaved run.
- Parallelism is per layer, joining before the layer above is composited, so layer order —
  and therefore the result — is untouched. Threads are capped at 8 and only used above
  128×128 pixels. A persistent pool would recover the remaining spawn cost; that is noted
  in the roadmap, not done here.
- `cargo run --release -p aurelia-render --example bench_composite` reproduces the table
  above and prints the CPU, core count and compiler version with it. Per-mode rows
  (27.9–84.8 MPix/s across all 13 modes) make a slow mode visible instead of averaging it
  away behind Normal.
